GitHub Sync — Shared multi-user storage

Multiple users can work at the same time by storing the shared database as a JSON file in a GitHub repository. Each user pulls before editing and pushes after saving. Use a private repository.

Important: GitHub is not a real-time database. Concurrent edits to the same record can overwrite each other (last push wins). Prefer one editor per staff record at a time. Always Pull before major edits and Push when finished.

Setup steps
1. Create a private GitHub repository.
2. Optionally create an empty file data/vnh_store.json with content {"employees":[],"users":[]}.
3. Create a Fine-grained or classic PAT with repo (contents read/write) on that repository.
4. Enter owner, repo, path, and token above → Save → Pull.
5. Host this HTML via GitHub Pages (or open the file). Each staff member uses the same repo settings and their own login account from the shared Users list.

Security: The PAT is kept in sessionStorage only (cleared when the browser tab is closed). Never commit a token into the HTML file or a public repo. Prefer fine-grained tokens limited to one private repository.

Help — Multi-user, storage & conflict resolution

Simultaneous login: Yes. Each person opens the same GitHub Pages URL (or local copy), signs in with their account, Pulls shared data, works, then Pushes.

Where data lives: Canonical shared copy = JSON file in your private GitHub repo. Local IndexedDB is a per-browser cache for speed and offline use.

Not real-time (GitHub mode): Two people editing the same employee at once can overwrite each other (last Push wins). Prefer one editor per staff record. Always Pull before major edits and Push when finished.

Workflow: Pull → edit → Save → Push. Top bar has quick Pull/Push buttons.

1. IndexedDB conflict resolution strategies

IndexedDB is local to each browser profile. Conflicts appear when (a) multiple tabs on the same machine write the cache, or (b) local cache diverges from the GitHub shared file after offline edits.

StrategyHow it worksIn this app
Last-write-wins (LWW) Newest timestamp or version replaces older data. Simple; may drop concurrent edits. GitHub Push uses file SHA; if remote changed, push fails until you Pull (see optimistic locking below).
Optimistic concurrency (SHA / version) Read current version (SHA). Write only if SHA still matches. On mismatch → conflict → reload and retry. Implemented for GitHub: githubPush() re-fetches SHA; HTTP 409 / SHA mismatch → “Pull, then Push again”.
Pull-before-edit Always refresh shared state before opening a record for editing. Recommended workflow. Auto-Pull runs after login when GitHub is configured.
Record-level locking (soft) Mark a record as “being edited by X until T”. Others see a warning. Not built-in (would need real-time presence). Coordinate by section or staff name.
Merge by field / CRDT Merge non-overlapping field changes; use CRDTs for automatic merge. Not implemented (complex). Manual merge: Pull, re-apply your field changes, Push.
Tab-level coordination BroadcastChannel or storage events notify other tabs on the same origin. Local cache is single-writer per save; avoid editing the same log in two tabs.
Snapshot + audit Keep previous versions (Git history on GitHub provides this). Each Push is a Git commit — use GitHub history to recover an overwritten version.
// Optimistic concurrency pattern used on Push const check = await fetch(contentsUrl); // current remote file const { sha } = await check.json(); const put = await fetch(contentsUrl, { method: "PUT", body: JSON.stringify({ message, content: base64, sha, branch }) }); if (put.status === 409) { // Remote changed since our last Pull — resolve by Pull → merge → Push }

Practical rule for the laboratory: one person edits one staff record at a time; always Pull first; Push when done; use GitHub commit history if something was overwritten.

2. Firebase Realtime Database — investigation

Firebase Realtime Database (RTDB) is a cloud-hosted JSON tree with live listeners. It is a strong option when true simultaneous multi-user editing is required beyond GitHub file sync.

TopicFinding
What it isNoSQL JSON tree; clients subscribe with on("value") / on("child_changed") and receive updates in milliseconds.
Multi-userDesigned for concurrent clients. Security Rules control read/write per path (e.g. per lab, per role).
Conflict handlingLast write to a path wins at the leaf; use transactions (transaction()) for counters or conditional updates; structure data so different users write different paths when possible.
OfflineOfficial SDKs keep a local cache and queue writes; sync when back online (similar role to our IndexedDB cache).
AuthFirebase Authentication (email, Google, etc.) + custom claims for Principal Lab roles — maps cleanly to our RBAC privileges.
vs GitHub syncGitHub: simple, private repo, free, audit via commits, not real-time. Firebase: real-time, presence, finer rules, needs Firebase project & SDK, usage quotas/billing at scale.
vs FirestoreFirestore is document/query oriented; RTDB is a live JSON tree. Either can host this lab schema; Firestore often preferred for new apps with complex queries.
Data shape (example)/labs/vnh/employees/{id}, /labs/vnh/users/{uid}, /labs/vnh/meta/updatedAt — avoid one giant root blob so concurrent edits touch different nodes.
Security Rules (sketch)Allow read if authenticated; allow write if auth.token.role in admin/principal/scientist…; validate required fields server-side in rules.
This HTML app todayUses GitHub Contents API + IndexedDB. Firebase is not embedded (would need project API keys and the Firebase JS SDK). Migration path: keep the same UI; replace githubPull/Push with RTDB get/set/on listeners.

Recommendation: Keep GitHub sync for a private lab repo if staff count is small and edits are coordinated. Move to Firebase (or Supabase) when you need live multi-user editing, presence (“user X is editing…”), and server-enforced security rules without managing a custom backend.

3. CRDT algorithms (explore)

CRDT (Conflict-free Replicated Data Type) structures merge concurrent updates without central locks. Useful when multiple lab workstations edit offline and later sync.

Algorithm / typeBehaviourFit for this log
G-Counter / PN-Counter Grow-only or increment/decrement counters that merge by taking per-replica max then summing. Total CPD points across replicas; not ideal as sole store for full employee records.
G-Set / 2P-Set / OR-Set Sets that only add (G-Set), or add+remove with tombstones (2P-Set / observed-remove set). OR-Set suits lists of activity rows or attachment IDs when two users add different rows offline.
LWW-Register / LWW-Element-Set Each field keeps (value, timestamp). Merge keeps the highest timestamp. Simple per-field merge for name, outcome, dates. Clock skew can mis-order events.
MV-Register Keeps all concurrent values until a user resolves the conflict. Good UX for “two outcomes set offline” — surface both and let QM choose.
RGA / WOOT / Yjs-style sequences Ordered sequences for collaborative text; complex. Overkill for form fields; relevant only if free-text notes were co-edited live.
JSON CRDTs (Automerge, Yjs Doc) Map CRDT operations onto nested JSON documents. Best long-term approach for full employees[] documents if moving beyond GitHub LWW.
// Conceptual LWW field merge (not a full CRDT library) function mergeEmployee(local, remote) { const out = { ...remote }; for (const key of Object.keys(local)) { if (key === "id") continue; const lt = local._meta?.[key]?.ts || 0; const rt = remote._meta?.[key]?.ts || 0; out[key] = lt >= rt ? local[key] : remote[key]; } // Activities: OR-Set style — union by activity id const byId = new Map(); for (const a of [...(remote.activities||[]), ...(local.activities||[])]) { if (a.id) byId.set(a.id, a); } out.activities = [...byId.values()]; return out; }

This app today: GitHub sync is file-level optimistic LWW (SHA check), not a field-level CRDT. CRDTs would be introduced with a library (e.g. Automerge) or a backend (Firebase/Firestore) that stores operations. Practical rule remains: one editor per staff record when using GitHub Push.

4. Firebase Firestore — check

Firestore is Firebase’s document database. Compared with Realtime Database, it uses collections/documents, richer queries, and different pricing/offline behaviour.

TopicAssessment for VNH Staff Log
Data modelCollection employees with one document per staff member; subcollections for activities / achievements if lists grow large.
Multi-userRealtime listeners (onSnapshot) update all clients. Concurrent writes to different documents do not conflict.
ConflictsLast write per document field wins unless you use transactions or batched writes. Security Rules enforce who can edit.
QueriesFilter by section, outcome, authReview ≤ date — stronger than RTDB for dashboard KPIs.
OfflinePersistent local cache built into the SDK; writes queue and resolve when online.
vs RTDBPrefer Firestore for structured lab records and queries; RTDB for simple live presence / typing indicators.
vs GitHub fileFirestore: true multi-user, no manual Pull/Push, path always defined by collection IDs. GitHub: simple ops ownership, commit audit, no Firebase bill.
SecurityRules example: allow write if request.auth != null && request.auth.token.role in ['admin','scientist',…].
This HTMLFirestore is not wired in (needs Firebase project + SDK). Documented as the upgrade path when GitHub LWW is insufficient.
// Conceptual Firestore shape (not active) // employees/{employeeId} // { name, staffId, section, outcome, authReview, updatedAt, updatedBy } // employees/{employeeId}/activities/{activityId} // employees/{employeeId}/achievements/{achId} import { getFirestore, collection, doc, onSnapshot, setDoc } from "firebase/firestore"; const db = getFirestore(); onSnapshot(collection(db, "labs", "vnh", "employees"), (snap) => { store.employees = snap.docs.map(d => ({ id: d.id, ...d.data() })); renderEmployeeList(); }); await setDoc(doc(db, "labs", "vnh", "employees", id), emp, { merge: true });

Path note: Firestore paths are collection/document segments (no “missing file path”). GitHub mode requires an explicit repo file path — validated and defaulted to data/vnh_store.json in this app.
